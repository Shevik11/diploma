# Структурований план дипломної роботи
## Дослідження мінімальних конфігурацій для розгортання SLM

---

## 1. Вступ та Цілі Дослідження

### 1.1 Постановка задачі

Сучасні малі мовні моделі (SLM) стають дедалі доступнішими для розгортання на локальному обладнанні та у хмарі. Ключове питання для практичного застосування — яка мінімальна конфігурація апаратного забезпечення дозволяє моделі працювати прийнятно: без критичних затримок, без збоїв через нестачу ресурсів, з адекватною швидкістю генерації токенів.

### 1.2 Основні завдання

- Визначити мінімальні вимоги до RAM, CPU та відеопам'яті для кількох SLM-моделей
- Запустити серію тестів при різних конфігураціях ресурсів (обмеження через контейнери або налаштування VM)
- Зафіксувати поріг «ще ок» — мінімальну конфігурацію, при якій модель видає результат за прийнятний час
- Проаналізувати вартість хмарних інстансів, що відповідають знайденим мінімальним конфігураціям
- Скласти рекомендації щодо вибору конфігурації залежно від бюджету та вимог до швидкості

## 3. Методологія Тестування

### 3.1 Принцип обмеження ресурсів

Тести запускаються у Docker-контейнерах з явно виставленими лімітами RAM і CPU-ядер. Це дозволяє точно контролювати доступні ресурси без потреби у фізичній зміні конфігурації машини.

### 3.2 Матриця конфігурацій

| RAM (ГБ) | CPU (ядра) | GPU VRAM | Очікуваний результат |
|---|---|---|---|
| 1 | 1 | Без GPU | Очікується відмова або дуже повільна робота |
| 2 | 2 | Без GPU | Мінімальний поріг для малих моделей |
| 4 | 2 | Без GPU | Базова конфігурація для моделей 1–3B |
| 4 | 4 | Без GPU | Покращена продуктивність CPU-інференсу |
| 8 | 4 | Без GPU | Комфортна конфігурація для 3–7B |
| 4 | 2 | 2 ГБ VRAM | GPU-прискорення на мінімальній конфігурації |
| 8 | 4 | 4 ГБ VRAM | GPU-прискорення на стандартній конфігурації |
| 16 | 8 | 8 ГБ VRAM | Висока продуктивність, референсна точка |

### 3.3 Типи тестів

- **Cold start:** запит одразу після завантаження контейнера
- **Warm запит:** запит після «прогріву» (модель вже в пам'яті)
- **Серія послідовних запитів:** 10 запитів підряд, фіксується середнє та медіана
- **Граничний тест:** поступове зменшення RAM до відмови моделі

### 3.4 Тестові промпти

- **Короткий:** «Поясни, що таке Docker, у 2-3 реченнях» (~50 токенів виводу)
- **Середній:** «Напиши функцію на Python для сортування списку» (~150 токенів виводу)
- **Довгий:** «Поясни різницю між контейнерами та віртуальними машинами детально» (~300 токенів виводу)

## 4. Метрики Продуктивності

### 4.1 Основні метрики інференсу

| Метрика | Опис | Одиниця | Поріг «ок» |
|---|---|---|---|
| Time to First Token (TTFT) | Час до появи першого токену | мс | < 3000 мс |
| Tokens per Second (TPS) | Швидкість генерації | tok/s | > 3 tok/s |
| Total Response Time | Повний час відповіді | с | < 30 с |
| Model Load Time | Час завантаження моделі | с | < 60 с |

### 4.2 Використання ресурсів

- **Peak RAM usage:** максимальне споживання пам'яті під час генерації
- **Average CPU utilization:** середнє завантаження CPU під час інференсу
- **VRAM usage:** обсяг відеопам'яті (якщо використовується GPU)
- **OOM events:** чи виникли помилки out-of-memory

---

## 5. Інструменти

- **Ollama** — основний інструмент для запуску GGUF-моделей через REST API
- **llama.cpp** — альтернатива з детальним контролем параметрів
- Docker: `--memory`, `--cpus` для обмеження ресурсів
- Python + `requests` + `time` — вимірювання TTFT та TPS
- Prometheus + Grafana — агрегація метрик
